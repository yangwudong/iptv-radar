## 二、光猫与软路由的关系

### 2.1 角色分工
```
电信PON光纤
    │
[光猫 HS8125C] ── 桥接模式(二层透传) ────────────────
    │  职责: 1)把电信的多个VLAN透传给软路由
    │       2)IPTV组播的IGMP Proxy(组播转发唯一通道,关掉全部频道不通)
    │       3)不做NAT/拨号/路由(那些交给软路由)
    │
    ├── 光猫口A ──→ 软路由 eth1  (透传: PPPoE上网 + IPTV VLAN43)
    │
[软路由 OpenWRT] ── 职责: PPPoE拨号 + NAT + 防火墙 + 路由 + IPTV接入
    │
    ├── eth0 → br-lan → 家庭LAN(所有设备)
    └── eth1 → WAN(PPPoE) + eth1.43(IPTV)
```

**核心理解**:
- 光猫是**桥接模式**,只当"二层透传管道 + 组播IGMP代理",所有智能(拨号/NAT/路由/防火墙)在软路由上做
- 电信在光猫侧划分了多个VLAN(见2.2),光猫把它们透传到软路由,软路由按VLAN tag区分处理
- **光猫的IGMP Proxy不能关** — 它是组播流进入家庭网络的唯一通道,关掉后连200/201段组播也全不通

### 2.2 电信侧 VLAN 划分(光猫透传)
| VLAN | 用途 | 软路由侧处理 |
|------|------|-------------|
| 41 | INTERNET (上网) | PPPoE拨号 → pppoe-wan (走eth1 untag) |
| 43 | OTHER / IPTV | DHCP+IPoE认证 → zIPTV接口 (走eth1.43 tag) |
| 46 | VOICE (电话) | 未用(电话口直接在光猫) |
| 4000 | 组播VLAN | 光猫内部处理,组播流承载 |

## 四、接线方式演进史

### 阶段1: USB网卡独立口(eth2) — 已弃用
```
光猫LAN2口 ──→ USB千兆网卡(AX88179) = eth2 ──→ zIPTV接口
```
- 优点: IPTV和上网物理隔离,两根线
- 缺点: **USB2.0锁死** — 协商100M,单流42M,多路上限89M;USB网卡发热+偶尔link抖动

### 阶段2: VLAN子接口(eth1.43) — 当前方案 ✅
```
光猫口(透传WAN+VLAN43) ──一根线──→ eth1 ──┬── untag → PPPoE上网
                                          └── VLAN43 tag → eth1.43 → IPTV
```
- 优点: **千兆口**,摆脱USB瓶颈;一根线;少个USB网卡(省电/更稳)
- 权衡: IPTV和上网共享eth1物理带宽,但千兆余量足(上网200M+IPTV32M ≪ 1000M),互不影响
- **对抢购/低延迟无影响**: VLAN tag逻辑隔离,抢购走untag/PPPoE路径没变;抢购拼RTT不拼带宽

### 迁移要点(阶段1→2)
1. 建VLAN设备: `type=8021q, ifname=eth1, vid=43, name=eth1.43`
2. zIPTV接口 device 从 `eth2` 改为 `eth1.43`(认证参数MAC/Option60/hostname全部保留)
3. **改hotplug路由脚本**: `dev eth2` → 动态获取`l3_device`(否则单播RTSP路由失效,4K播不了!详见六)
4. 光猫侧无需改动(那个口本就透传WAN+VLAN43)

## 五、IPTV 组播 vs 单播 实现原理

### 5.1 两种分发方式对比
| 对比项 | 组播(Multicast) | 单播(Unicast/RTSP) |
|--------|----------------|--------------------|
| 频道段 | 233.50.200.x / 201.x | 202.x频道 + 所有RTSP |
| 协议 | IGMP join + UDP组播 | EPG认证 + RTSP → UDP单播 |
| 组播地址 | 233.50.200/201.x:5140 | rtsp://115.233.40.137/... |
| 视频源 | 122.229.7.118(组播源) | 115.233.45.x(单播流媒体) |
| 本区域可用? | 200/201段✅ 202段❌ | ✅(绕过组播限制) |
| 带宽特点 | 固定,不随人数增加 | 每路独立,码率更高(RTSP 2-3.7倍) |
| 稳定性 | 约40%频道稳定 | 较稳定 |

### 5.2 为什么202.x频道要用单播?
**根因**: 233.50.202.x频道(4K卫视/凤凰等)在**本区域BRAS/OLT未推送组播流**。
- 组播join到202.x → 无流返回(上游根本没推这批组播)
- 机顶盒看202.x实际是走**EPG认证获取RTSP单播地址** → 从115.233.45.x收UDP单播流
- 抓包证实: 机顶盒对202.x的IGMP join = 0个,全走单播

### 5.3 组播实现路径(200/201段)
```
播放器 → msd_lite HTTP接口(http://<ROUTER_IP>:4088/rtp/233.50.201.x:5140)
       → msd_lite发IGMP join到组播地址
       → 经eth1.43 → 光猫IGMP Proxy → 上游组播源122.229.7.118
       → UDP组播流回传 → msd_lite转HTTP → 播放器
```
- **msd_lite**: 组播转HTTP单播的工具(端口4088,udpxy兼容接口)
- 组播不需要单播路由(六里那三条),因为目标是233.50.x.x本地组播

### 5.4 单播(RTSP)实现路径
```
播放器 → rtsp://115.233.40.137/PLTV/.../xxx.smil (RTSP入口)
       → 经eth1.43(需单播路由!见六) → RTSP服务器302重定向链
       → 普通频道1跳: 40.137 → 45.135 → 200 OK
       → 4K频道4跳: 40.137 → 220.191.136.24 → 41.137 → 136.24 → 122.229.6.193 → 200 OK
       → 从最终流媒体服务器收UDP单播流
```
- **必须有单播路由**让115.233/220.191/122.229走eth1.43,否则走PPPoE公网出口到不了IPTV专网
- RTSP URL简化版(去掉.smil后参数)可用,直播IP白名单认证,不需要token

### 5.5 EPG认证流程(获取频道列表+RTSP地址)
```
1. GET  115.233.40.140:33200/EPG/jsp/AuthenticationURL → EncryptToken
2. POST /EPG/jsp/authLoginHWCTC.jsp → 登录
3. POST /EPG/jsp/ValidAuthenticationHWCTC.jsp → Authenticator验证
   Authenticator = DES-ECB加密("99999$TOKEN$USERID$STBID$IP$MAC$$CTC", key="00000000")
4. POST /EPG/jsp/getchannellistHWCTC.jsp → 169个频道(组播地址+RTSP地址)
```
- 认证靠 DHCP Option 60(IPoE) + 克隆机顶盒MAC + STBID
- 脚本 epg_client.py 纯Python实现DES,可在OpenWRT裸奔

## 六、关键路由配置(单播RTSP的命脉)

EPG/RTSP服务器在IPTV专网,不在公网。必须加路由让这些IP走IPTV接口(eth1.43),
否则LAN设备/播放器走PPPoE公网出口到不了 → 单播4K播不了(但组播不受影响)。

| 目标网络 | 掩码 | 用途 |
|----------|------|------|
| 115.233.40.0 | /21 (255.255.248.0) | EPG(40.140)+RTSP入口(40.137/41.137)+流媒体(45.x) |
| 220.191.136.0 | /24 | EDS认证(136.23)+RTSP重定向(136.24) |
| 122.229.6.0 | /24 | 4K频道流媒体终点(6.193/6.195) |

**实现**: hotplug脚本 `/etc/hotplug.d/iface/99-iptv-routes`(zIPTV ifup时自动加,详见SPEC.md方案A)。
脚本用**动态设备名**(`l3_device`),自适应eth2/eth1.43。

> **⚠️ 血泪教训(2026-07)**: 切VLAN后设备名从eth2变eth1.43,但hotplug脚本写死了`dev eth2`,
> 导致三条单播路由失效 → **组播能播、单播4K全挂**。现象特征:组播正常单播不行 = 优先查这三条路由。

## 八、播放链路总览(从设备到画面)

### 组播频道(如CCTV1, 233.50.201.118)
```
APTV → http://<ROUTER_IP>:4088/rtp/233.50.201.118:5140
     → msd_lite(软路由) → IGMP join → eth1.43 → 光猫IGMP Proxy
     → 组播源122.229.7.118 → UDP组播流 → msd_lite转HTTP → APTV播放
```

### 单播4K频道(如北京卫视4K)
```
APTV → rtsp://115.233.40.137/PLTV/.../128124469.smil
     → 单播路由(115.233.40.0/21 via eth1.43) → RTSP重定向链
     → 122.229.6.193 → UDP单播流(~32Mbps, 4K@50fps HDR) → APTV播放
     ⚠️ APTV需关闭"组播FCC优化"(实验性功能对单播有bug会卡顿)
```

## 九、常见故障速查

| 现象 | 大概率原因 | 排查 |
|------|-----------|------|
| 组播能播,单播4K不能 | 单播路由失效(设备名/网关错) | `ip route \| grep 115.233`,查hotplug脚本dev |
| 全部频道不通 | 光猫IGMP Proxy关了 / eth1.43没起 / DHCP没认证 | `ifstatus zIPTV`,`ip addr show eth1.43` |
| 单播4K卡顿(组播正常) | APTV"组播FCC优化"bug / 带宽 | 关FCC优化;开RTSP over TCP |
| 换台慢 | RTSP重定向链长(4K 4跳) / 重定向死循环 | 追踪重定向链是否循环 |
| CPU异常高 | tailscaled连不上节点空转 | 查`tailscale status`离线节点,修复连通性 |
| IPTV拿不到IP | Option60过期 / MAC没克隆 / VLAN没通 | 查sendopts/macaddr,抓DHCP包 |
