# 浙江电信 IPTV 工作原理

> 本文讲清楚: 电信局端如何推送IPTV资源、有哪些分发方式、官方EPG如何访问、
> 组播和单播各自的要求。以及一个真实的深度分析案例(杭州市区可看/萧山不可看)。
>
> ⚠️ 文中IP/账号等已脱敏为 `<占位符>`,真实值见本地 .env

---

## 一、IPTV 资源分发的全貌

电信 IPTV 不是"一种"技术,而是**多种分发方式并存**,机顶盒按频道类型选择:

```
                       电信城域网/BRAS
                            │
        ┌───────────────────┼────────────────────┐
        │                   │                     │
   [组播分发]          [单播分发/RTSP]        [EPG中间件]
   IGMP + UDP组播      RTSP → UDP单播         HTTP(华为HWCTC)
   233.50.200/201.x    115.233.45.x          115.233.40.140:33200
   低成本/一对多        按需/一对一            认证+频道表+节目单
        │                   │                     │
        └───────────────────┴─────────────────────┘
                            │
                       [机顶盒/软路由]
```

### 1.1 三种分发方式对比

| 维度 | 组播(Multicast) | 单播RTSP(Unicast) | EPG中间件 |
|------|----------------|-------------------|-----------|
| 协议 | IGMP join + UDP | RTSP协商 + UDP单播 | HTTP |
| 地址 | 233.50.200/201/202.x | rtsp://115.233.40.137/... | 115.233.40.140:33200 |
| 带宽 | 固定(不随人数增加) | 每路独立占用 | 小 |
| 延迟 | 低 | 稍高(协商+重定向) | - |
| 适合 | 热门直播频道 | 冷门/4K/组播未覆盖 | 认证+获取频道表 |
| 局端要求 | BRAS需在本区域推流 | 流媒体服务器有内容即可 | 账号认证通过 |

**关键认知**: 同一个频道可能**同时有组播和单播两个地址**(EPG返回的频道表里都有)。
机顶盒优先用哪个,取决于本区域组播是否推送到位。

## 二、组播分发的要求

### 2.1 组播链路
```
组播源(122.229.7.118) → 城域网 → BRAS/OLT → 光猫(IGMP Proxy) → 机顶盒/软路由
                                    ↑
                          关键: BRAS必须在"本区域"推送这路组播
```

### 2.2 收组播的必要条件(缺一不可)
1. **IPoE认证通过** — DHCP Option60 + 克隆机顶盒MAC,拿到IPTV网段IP
2. **光猫IGMP Proxy开启** — 光猫是组播进入家庭网的唯一通道(桥接模式下也要开)
3. **本区域BRAS有推送这路组播** — ⚠️这是最隐蔽的坑,见第五节案例
4. **IGMP版本匹配** — 一般IGMPv2(v2/v3不是主要障碍,见案例排除项)

### 2.3 组播地址段(浙江电信)
| 段 | 状态 | 说明 |
|----|------|------|
| 233.50.200.x | 部分可用 | 多为SD备选源 |
| 233.50.201.x | 主源 | EPG官方地址,高清 |
| 233.50.202.x | **本区域(萧山)不通** | 4K卫视/凤凰等,BRAS未推送,只能走单播 |

## 三、单播RTSP分发的要求

### 3.1 RTSP链路(有重定向)
```
入口 115.233.40.137:554
  → 302重定向 → 中间调度(220.191.136.24)
  → 302重定向 → 实际流媒体(115.233.45.x 普通 / 122.229.6.x 4K)
  → 200 OK + SDP → UDP单播流
```
- **普通频道**: 1跳重定向(40.137 → 45.135 → OK)
- **4K频道**: 最长4跳(40.137 → 136.24 → 41.137 → 136.24 → 6.193 → OK)
- **故障模式**: 重定向死循环(136.24 把请求踢回40.137,无限循环)

### 3.2 收单播的必要条件
1. **EPG认证通过** — 拿到RTSP地址(在频道表里)
2. **能路由到RTSP服务器网段** — 115.233.40.0/21 + 220.191.136.0/24 + 122.229.6.0/24
3. **554端口可达** — 部分区域554被封(需从IPTV专网访问)
4. **RTSP URL格式**: 简化版(去掉.smil后参数)直播可用,IP白名单认证不需token

### 3.3 RTSP URL格式
```
完整版(带认证): rtsp://115.233.40.137/PLTV/88888913/224/xxx/yyy.smil?accountinfo=...&it=...
简化版(可用):    rtsp://115.233.40.137/PLTV/88888913/224/xxx/yyy.smil
```
`88888913` 是浙江电信运营商ID(公共,非个人隐私)。

## 四、官方EPG如何访问(华为HWCTC中间件)

### 4.1 认证流程
```
1. GET  <EPG_SERVER>/EPG/jsp/AuthenticationURL?UserID=<USERID>&Action=Login
        → 返回 EncryptToken
2. POST /EPG/jsp/authLoginHWCTC.jsp?UserID=<USERID>
        → 登录
3. POST /EPG/jsp/ValidAuthenticationHWCTC.jsp
        → 提交 Authenticator(DES-ECB加密), 验证
        Authenticator = DES加密("99999$TOKEN$USERID$STBID$IP$MAC$$CTC", key=<DES_KEY>)
        → 返回 JSESSIONID(认证成功)
4. POST /EPG/jsp/getchannellistHWCTC.jsp
        → 返回169个频道(名称+组播IP+RTSP地址+时移标志)
```

### 4.2 认证凭证从哪来
| 凭证 | 获取方式 |
|------|---------|
| UserID | 抓包DHCP/EPG请求,或机顶盒设置页 |
| STBID | = 固定前缀 + UserID + MAC (32位) |
| MAC | 机顶盒背面/设置页;软路由需克隆 |
| DES_KEY | 用 `legacy/find_key.py` 爆破(本例8位全0) |

详见 `03_EPG认证与频道获取.md`。

## 五、深度分析案例: 为什么杭州市区能看、萧山不能看?

> 这是本项目最有价值的分析。记录完整的排查方法论,便于以后遇到类似问题深入。

### 5.1 现象
- 软路由 msd_lite 转组播: `233.50.200/201.x` ✅,`233.50.202.x` ❌(4K卫视/凤凰等)
- 同一个光猫口,插电信原装机顶盒: 202.x **能看**
- 杭州**市区**用户反馈: 202.x 组播能收到
- **萧山区**(本地): 202.x 组播收不到

### 5.2 排查方法论(逐一排除,锁定根因)

**第一步: 排除本地配置问题** — 用机顶盒在同一光猫口测试
- 机顶盒能看202.x → 排除"光猫配置错误/端口绑定错误/账号问题"
- 结论: 不是家里的问题,是获取方式的差异

**第二步: 抓包对比机顶盒 vs 软路由** — MacBook桥接抓包(见 stb_boot_and_play.pcap)
```
关键发现(tshark过滤):
  ip.addr contains "233.50.202" → 0包!
  机顶盒看202.x时,根本没发IGMP join到233.50.202.x
  而是从 115.233.45.x 收UDP单播流(80万+包)
```
- **结论: 机顶盒看202.x用的是单播,不是组播!**

**第三步: 排除IGMP版本** — 对比能看202.x的市区用户抓包
- 市区大佬抓包也是IGMPv2 → 排除"v2/v3版本问题"
- (OpenWRT force_igmp_version=3 不生效是已知内核问题,但不是根因)

**第四步: 排除光猫IGMP Proxy** — 关闭测试
- 关闭后200/201.x也不通 → Proxy是必要条件,但不是202.x不通的原因

### 5.3 根因结论
**233.50.202.x 频道在萧山区不通过组播分发。**
- 萧山的 BRAS/OLT **没有把这批组播流推送到本区域**(可能因为4K频道成本高/该区域用户少/策略不同)
- 机顶盒看202.x实际是走**EPG单播(RTSP)**,不依赖组播
- 市区BRAS推送了202.x组播,所以市区能收到

对比表:
| 对比项 | 200/201.x(萧山可) | 202.x(萧山不可) |
|--------|------------------|-----------------|
| 分发方式 | 组播 | 单播(萧山) / 组播(市区) |
| 萧山BRAS推送? | ✅ | ❌ |
| 机顶盒怎么看 | 组播 | 单播RTSP |
| 软路由怎么看 | 组播✅ | 只能单播RTSP(绕过) |

### 5.4 我们的解决方案
- 200/201.x频道 → msd_lite组播转HTTP(稳定低延迟)
- 202.x频道 → EPG认证获取RTSP单播地址,绕过组播限制

### 5.5 还能不能让萧山收到202.x组播?(待深入)
可能的方向(未验证):
1. **打10000号报修** — 要求BRAS在本区域开通202.x组播(客服可能不懂组播概念,难)
2. **找是否有其他组播段** — 扫描是否遗漏了202.x在本区域的其他推送
3. **接受现状** — 用RTSP单播看202.x(当前方案,已能稳定观看)

以后若要深入,可重新抓包对比市区/萧山的完整BRAS交互,看协商差异。
