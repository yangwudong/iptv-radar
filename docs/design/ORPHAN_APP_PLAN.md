# 孤儿源识别 App — 实施计划书

> 创建: 2026-07-25
> 目标: 让「看画面认频道」这件事从「AI 陪着一起干」变成「你一个人 10 分钟能干完」。
> 前置契约: [ORPHAN_REVIEW.md §3](./ORPHAN_REVIEW.md) 的两个 json（已定死，不改）。

---

## 一、先说结论：建议不做 Electron

原设计（2026-07-24）写的是 Electron App。基于今天核实的事实，**我建议改成本地静态网页**（单个 HTML 文件 + 浏览器打开），理由如下。

### 核实到的事实

| 事实 | 实测结果 | 对方案的影响 |
|---|---|---|
| 待识别孤儿源数量 | **27 个**（17 组播 + 10 单播） | 一次性任务，不是长期高频操作 |
| 10 个单播孤儿是否有 token | **全部有** `timeshift_query`（529-555 字符） | 拼上 `?query` 就能播、能截图 |
| Mac 能否直连播放单播源 | **能**（ffprobe 拿到 h264 1920x1080） | App 可在 Mac 侧直接播放，不必只靠预生成截图 |
| 组播源能否在 Mac 播 | 能（经软路由 rtp2httpd 转 HTTP，或 rtp:// 直通） | 同上 |
| 现有截图产出 | **只给组播截图**，单播 0 张 | 需先修 `orphan_export`（见阶段一） |

### 为什么 Electron 不合适

| 维度 | Electron | 本地静态网页 |
|---|---|---|
| 工程量 | 项目脚手架 + 打包 + 签名 + 更新，≈ 数百行配置 | **一个 HTML 文件** |
| 维护成本 | Electron 大版本升级、Node 依赖、CVE 跟进 | 零依赖 |
| 播放 H.264 TS 流 | 需引 mpegts.js，且 Electron 内核限制同浏览器 | 同样能力（都是 Chromium） |
| 播放 H.265 / rtsp | **一样不行**（需外部播放器） | 一样，都调 IINA |
| 读本地截图 | 直接读文件系统 | `file://` 或起一个临时静态服务即可 |
| 写结果文件 | 直接写 | 浏览器下载到 `~/Downloads` |
| 分发 | 需打包 dmg/exe | 双击 HTML |

**关键判断**：Electron 唯一的实质优势是「直接读写任意本地文件」。但这个场景下，读截图可以用静态服务解决，写结果就是下载一个 json —— 都不值得为此引入一整个桌面应用框架。

而且这是**一次性任务**（27 个源，认完就没了；以后每月全量扫描可能新增几个）。为 27 个源建一个需要长期维护的 Electron 项目，ROI 是负的。

### 建议方案：`orphan-review.html`（单文件网页）

- pipeline 生成待识别包时，**顺带生成一个自包含的 HTML**（数据内联进去，不需要 fetch json，避免 CORS）
- 你把 `output/orphan_review/` 整个目录从 NAS 拷到 Mac（或直接用 NAS 的 nginx 发布），浏览器打开 HTML
- 逐个看截图 → 选决定 → 点「导出」→ 下载 `resolved_<时间>.json`
- 把 json 放回 NAS 的 `data/orphan_inbox/`，下次 pipeline 自动落库

**契约完全不变** —— `orphans.json` / `resolved.json` 还是那两个，只是消费端从 Electron 换成一个 HTML。将来真要做 Electron，契约照样能用。

## 二、分阶段实施

### 阶段一：修 `orphan_export` 的两个缺陷（必做，否则 App 白做）

**缺陷 A：单播源不截图**
`orphan_export.py` 的 `need_shot` 条件写死 `stype == 'multicast'`，所以 10 个单播孤儿在待识别包里**一张截图都没有**，App 打开只能看到一串地址 —— 认不出来。

已核实这 10 个源都有 token query，拼 `address + '?' + timeshift_query` 就能抓帧。

**缺陷 B：单播 `play_url` 是裸 rtsp 地址**
```python
def play_url(source_type, address, msd):
    if source_type == 'multicast':
        return f"http://{msd}/rtp/{address}"
    return address          # ← 裸地址,缺 token,播不了
```
需要拼上 query。另外应同时给出**两个** URL：
- `play_url`：给外部播放器（IINA）用的完整 rtsp 地址
- `http_url`：经 rtp2httpd 转 HTTP（`/rtsp/host:554/path?query`，本轮已验证可用）—— 浏览器内置播放器可能能播（h264 TS），值得给出

**验收**：待识别包里 27 个源**每个都有 3 张截图**，且 `play_url` 直接能播。

**风险**：给 10 个单播源截图会增加 pipeline 耗时（10 × 3 张 × 最多 20s = 最坏 10 分钟）。缓解：截图已有复用机制（本轮刚做），只有新孤儿才拍。

---

### 阶段二：生成自包含 HTML（App 主体）

在 `orphan_export.py` 末尾多产出一个 `orphan-review.html`，用 Jinja2 模板（项目已有 `template_util.py`，风格与 Dashboard 一致）。

**必须有的功能**（按重要性排序）：

1. **一屏一个源**：大图轮播 3 张截图（← → 切换）+ 技术信息（分辨率/编码/帧率/音频）
2. **频道选择器**：从 `channels` 列表做**模糊搜索**下拉（143 个频道，必须能搜，不能纯下拉）
3. **五个 action 按钮**：归并已有 / 新建频道 / 垃圾 / 未知 / 跳过
4. **播放入口**：
   - 「用 IINA 播放」按钮 → `iina://` 协议（Mac 一键调起）
   - 「复制地址」按钮 → 给其他播放器用
   - （可选）内置 `mpegts.js` 播 HTTP 流 —— 组播可行，单播转 HTTP 后 h264 也应可行，但**别把它当主要手段**，H.265 和意外情况都要退回 IINA
5. **进度与草稿**：`X/27 已决定`；决定存 `localStorage`，关掉网页再打开不丢
6. **导出**：生成 `resolved_<时间>.json` 下载，并显示「放到 NAS 的 `data/orphan_inbox/`」提示

**键盘操作**（27 个源，键盘能省一半时间）：
- `↑/↓` 或 `J/K`：上一个/下一个源
- `1`~`5`：快速选 action
- `/`：聚焦搜索框
- `Enter`：确认并跳下一个

**明确不做**：
- 不做登录/多用户/权限
- 不做直接写 NAS（那需要后端，破坏「无常驻服务」原则）
- 不做自动识别/OCR（AI 辅助是另一条路，见阶段四）

---

### 阶段三：端到端验证（用真实的 27 个源）

按项目既有规矩来，不能只看「跑起来了」：

1. **备份**：`cp data/iptv.db data/iptv.db.bak-orphan-<ts>` + 备份 `source_links.json`
2. **黄金基线**：先存下当前三套 m3u
3. **`--dry-run` 先行**：`orphan_import.py` 有 dry-run，先验证决定能被正确解析、不写库
4. **小批量真跑**：先只处理 2-3 个源（比如 1 个 `assign` + 1 个 `junk`），落库后检查：
   - `sources.channel_id` / `channel_key` 正确
   - `source_links.json` 快照已更新（**新格式** `{channel_id, channel_key}`）
   - `junk` 的源挂到 `__JUNK__` 且**不进 m3u**
5. **验证幂等**：同一个 resolved.json 再消费一次，不应重复建频道
6. **验证不被打回**：跑一次完整 `link_sources`，确认标记的 `junk`/`unknown` **没有变回孤儿**
   （这是本轮修的那个 bug —— 早期 `enabled=0` 的占位频道会被打回孤儿，标记全白做）
7. **对比黄金基线**：`assign` 的源应让对应频道出现/换源；其余频道 m3u 不应变化
8. 全部通过后再处理剩余源

---

### 阶段四（可选）：AI 辅助预填

27 个源里 17 个是组播（大概率是 BesTV 那批垃圾流），10 个单播是「名字对不上的正常频道」。

可以在阶段一之后、阶段二之前，先让我用图像识别跑一遍 27 个源的截图，**产出一个预填好的 `resolved.json` 草稿**，你在 App 里只做「确认/修正」而不是「从零判断」。

**这一步很可能让 App 变得可有可无** —— 如果 AI 预填准确率高，你直接 review 那个 json 就完事了。

所以我建议的执行顺序是：**阶段一 → 阶段四（AI 预填）→ 看情况决定还要不要阶段二**。

## 三、工作量与风险

| 阶段 | 工作量 | 风险 | 是否必做 |
|---|---|---|---|
| 一：修 orphan_export | 小（~30 行 + 测试） | 低（有测试护栏） | **必做** |
| 四：AI 预填草稿 | 小（跑一遍图像识别） | 低（只产出草稿，不写库） | 建议先做 |
| 二：自包含 HTML | 中（~400 行 HTML/JS + 模板） | 低（纯前端，不碰库） | 看阶段四结果 |
| 三：端到端验证 | 中（按 7 步走） | **中**（要写库，必须先备份） | **必做** |

**最大的风险不在 App，在阶段三的落库**。`orphan_import` 虽然写过、测过 5 种 action，但**从未在真实数据上跑过**。所以阶段三的 dry-run + 小批量 + 幂等验证不能省。

---

## 四、需要你决定的三件事

1. **要不要放弃 Electron，改成单文件 HTML？**（我的建议：是）
2. **要不要先做 AI 预填**（阶段四）？可能省掉整个阶段二。
3. **待识别包怎么从 NAS 传到 Mac？**
   - a) `scp -O` 手动拷（最简单，一次性任务够用）
   - b) 放到 nginx 发布目录，浏览器直接访问（省一步拷贝，但要注意那 10 个单播地址**含真实 token**，虽然只在内网）

我倾向 **1=是、2=先做、3=a**，理由都是「一次性任务，别过度工程」。
